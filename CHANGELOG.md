## 0.1.0 — first release

The first version of Zotero ChatGPT, published as an **unsigned early preview** for macOS on Apple
Silicon with Zotero 9.0.6. It is a single add-on with two modes that share one sidebar and one view
of the paper you have open.

**Chat** hosts the official `chatgpt.com` application inside the Zotero reader sidebar, so the
conversation, composer, streaming, model picker, history and uploads are the real ChatGPT web app
rather than a reimplementation. Opening the sidebar, reading a paper and switching papers start no
Codex work, and Chat never consumes Codex quota. Because the hosted page owns its own conversation,
the sidebar adds only what the page cannot know — the paper you are reading — through two one-click
clipboard actions: **Copy paper context** (local bibliography: title, authors, publication, year,
DOI and the stored abstract) and **Copy PDF file** (the actual file, ready to paste into ChatGPT's
own composer). Automatic PDF context is on by default, described before the first send, and can be
turned off.

**Agent** runs the bundled Codex App Server for work that changes your library, and it proposes
rather than acts: nothing is written until you review and approve it. **Highlight key points** uses
the model's verbatim quote plus a page hint, and the program verifies a unique match against the
frozen PDF revision before any native highlight is created, so invented coordinates cannot reach
your library. **Organize selected items** adds tags and collection memberships to the regular items
selected in the main window. **Get an article** resolves a DOI or public article URL and saves
restricted metadata, then attempts a lawful open-access PDF. A task is previewed and approved once
rather than item by item, and every write is preceded by an intent record and followed by a readback
and ledger entry, so a stop or a conflict can be told apart from a success and undone.

The sidebar is one row: the mode switch, the paper, the two copy actions, then new chat, history and
more. Switching modes never stops or discards work already running, each mode keeps its own draft,
focus and scroll, and the reader keeps Zotero's native dock, zoom, rotation and reading position.

**Known limitations of this release**

- The build is **unsigned**, and its manifest carries no update channel: Zotero will not find
  updates for it, and a reinstall is required to move to a later build.
- It runs on **macOS Apple Silicon only**. The bundled Codex runtime is a `darwin/arm64` binary.
- **Agent is experimental.** The full Agent path — a real model candidate through native write,
  readback and conflict undo — has not been re-verified on this artifact. Fetching open-access PDFs
  from a DOI or article link is the least settled part of it.
- Chat's own conversation is the web application's, so the plugin keeps only its local bindings,
  drafts and settings, not a copy of your ChatGPT history.

## Unreleased

### Development preview `0.4.0-alpha.1`

- **A hidden sidebar surface stops working, and the no-model host check can see the redesigned header again.** A hosted Chat surface that was hidden — switching to Agent, or closing the sidebar — kept its 500 ms timer running: the window kept waking up to re-measure, probe the official page and track the conversation until that surface was evicted or the window closed. Hiding now stops the poll and showing the surface starts a fresh one, so a parked paper costs nothing. This round also removed unused exports, an unreferenced stylesheet rule, and the dead compile-time `CHAT_TRANSPORT` branch in the Zotero entry point: this build never wires a native Chat transport, so the local Chat path still refuses honestly instead of borrowing Agent's Codex runtime. The dedicated-profile, no-model host stage runs to completion again — five driver assertions still read the pre-redesign DOM (the tab strip, the active-citation line and the `+` / history controls now live in the common shell, not in the chat section) or the old copy (`New chat` where Agent now says `New agent`, and the Preferences language canary looked for `Chat` / `Appearance` where the section is now `General`), which had been aborting the stage after 18 of 47 checks. The development add-on version stays `0.4.0a34`; the same-named development artifact was rebuilt in this round, so its SHA-256 changed.
- **One-row sidebar header, bibliography-only paper copy, and history deletion that stays deleted.** The common header is now a single row: the mode switch, the session title, the two paper actions, then `+` / history / `More`. The permanent `Current PDF · … pages read locally` line, the legacy action strip and the standing success/preparation lines are gone from the normal state — the next-send scope, the local read coverage and the automatic-PDF state live in `More → Paper & context details`, and the first outbound notice is a state that appears inside that header only while it is still owed. **Copy paper context** and **Copy PDF file** are icon buttons in that row (32 × 32 hit area, one 18 px icon baseline, localized title + explanation tooltip readable by keyboard and assistive technology), in the same position in both modes. Copy paper context now writes only the local bibliography — `Title` / `Authors` / `Publication` / `Year` / `DOI` and the stored `Abstract`, with missing fields omitted and no invented values — and shares no formatter with the automatic PDF text a real send carries, so trimming the manual copy cannot shrink what ChatGPT receives. A bare PDF with no provable bibliographic fact disables that action with a stated reason while the file action stays available. Deleting a local chat in the Preferences pane now updates an open sidebar History immediately (no restart, mode switch or refresh), an older list read that lands after the deletion cannot put the row back, a stale in-memory conversation cannot rewrite a removed chat into existence, and the row menu replaces the permanent delete cross with one confirmed `Delete local conversation…`. The reader document's inlined stylesheet is also refreshed when it differs from the running build, so an in-place add-on upgrade can no longer render new markup with the previous version's CSS. The development add-on version stays `0.4.0a34`; the same-named development artifact was rebuilt in this round, so its SHA-256 changed.
- **Chat mode now hosts the real `chatgpt.com` web application inside the sidebar.** Selecting `Chat` shows the actual ChatGPT page in the conversation area — its own conversation list, composer, streaming, model picker, history and upload controls — instead of a reimplementation of it, and `Agent` remains the native Codex surface on the same mode switch. The page is a top-level document in a host-created browser kept alive off-screen when it is not shown, so switching to `Agent`, closing the sidebar, switching PDFs or resizing the window does **not** reload it: the signed-in session and the open conversation stay where they were. Chat mode still starts no Codex work (no thread, turn, task, approval or reading job), and the previous native chat path with its placeholder transport is no longer the shipped Chat experience. Because the hosted application owns its own conversation and there is no supported way to inject context into it, the Chat bar adds exactly what the web app cannot know — the paper you have open — as one-click clipboard actions that say plainly what they did: originally **Copy paper context** (the locally read page text), **Attach current PDF** (the actual PDF file on the clipboard, ready to paste into ChatGPT's own composer so its own upload path runs) and **Copy selection**. *(Superseded by the one-row-header change above: the two paper actions are now icon buttons in the common toolbar, `Copy paper context` copies the local bibliography instead of page text, and `Copy selection` is no longer a toolbar action — the reader's own selection actions keep their route.)* Nothing is injected into the page, no ChatGPT markup is driven, no credential is read, and no undocumented endpoint is called. The development add-on version moves to `0.4.0a18`. Verified in the real host: the surface covers the sidebar slot, the browser reports the application URI, `Agent → Chat` keeps the same element and document, and both clipboard routes are read back and matched. Signing in, conversations, streaming, model selection, history, uploads and restart persistence remain manual verification.
- Split **Chat and Agent into two sibling execution paths inside the runtime**, not just in the presenter. A chat request now reaches a real `ChatExecutor` through an explicit `ExecutionRouter`, and it never creates a Codex thread, resumes a thread, starts a turn, runs the reading coordinator or creates a task — so it consumes no Agent execution quota. The previous behaviour (every request entering the Codex runtime and being "turned down" there) is gone: the strongest acceptance test now spies the Codex entry point (`thread/start`, `thread/resume`, `turn/start`, `turn/interrupt`) and proves a chat request never hits it while an agent request always does. **Chat's actual model transport is an unresolved platform integration boundary**: this build ships an honest placeholder, so a chat send fails with a clear "switch to Agent mode" message rather than silently becoming a tool-free Codex turn. Complex or long chat prompts are still chat (no automatic escalation), a chat request that reads as an action is refused without writing anything, the two modes keep sharing one conversation and one current-PDF context, an interrupted chat request is no longer marked "uncertain" (it has no native work to reconcile, so it simply fails), and Stop aborts the chat transport instead of sending `turn/interrupt`. A development-only trace (`ReaderOptions.trace`) can print the real path. The development add-on version moves to `0.4.0a15`.
- Fixed the **Chat / Agent mode switch** after owner feedback that the `Chat` option could not be selected and that ordinary questions still ran through the action path. Two root causes: the composer helper dropped the caller's CSS class for a text button, so the options rendered with the generic button skin and the pressed fill (`aria-pressed`) never applied; and the Chat/Agent boundary was only enforced by the presenter. The options now carry `.zchatgpt-mode-option` and show the selected mode, and the **runtime enforces the boundary**: the session service refuses any request that is not in Agent mode while carrying Agent work (a multi-pass reading batch or a non-`read` skill), and the reading coordinator refuses to create a job from a Chat request and freezes every step as Agent. A plain Chat question still reads and uses the current PDF, and complex questions are refused with a "switch to Agent" prompt rather than escalated. Both modes still share one model transport — there is no second quota system or hidden meter; the difference is that Chat creates no reading job or native task. The development add-on version moves to `0.4.0a14`.
- Renamed the project to **Zotero ChatGPT**: repository and npm `zotero-chatgpt`, display name "Zotero ChatGPT", XPI `zotero-chatgpt-<version>-dev.xpi`, addon id `{90909501-7b5b-4985-9f55-566e9890746c}`, runtime state under `zotero-chatgpt/v1/`, preferences under `extensions.zchatgpt.*`, bundle `content/zchatgpt.js`, and annotation provenance `[AI · Zotero ChatGPT]`. The development addon version moves to `0.4.0a11`. This is a **re-identity, not a cosmetic rename**: the renamed build is a different addon from earlier previews, records under the old storage directory are not read (no migration is implemented, and the old directory is left in place), and AI annotations written before the rename no longer match the new provenance string.

- Documented the **Chat Mode / Agent Mode** product architecture: Chat Mode is the first-class read-only conversational reader (automatic current-PDF context, retrieval, page/quote citations), Agent Mode adds Zotero/file actions on the same shared document context and conversation, and the currently opened PDF is treated as implicit context rather than a manually attached file. Docs only; no behavior change.
- Implemented the **Chat / Agent mode switch** as a user-visible per-chat control at the start of the composer (segmented `Chat` / `Agent`). The chosen mode is captured when a request is submitted and **frozen for that request**, so switching afterwards never re-labels an earlier turn; the next turn uses the new choice. Default is Chat.
- **Chat Mode is structurally read-only**: Agent-only skills (annotation and acquisition/diagram) are refused before any model request, document read or task is created, and the task/approval surface stays hidden. Chat Mode therefore does not require the action infrastructure at all.
- **Chat and Agent now run on two named execution paths** instead of branches of one submit. In Chat mode a natural-language request to change the library (for example "highlight this") is refused up front with a prompt to switch to Agent mode instead of being silently turned into a write, and a context large enough to need multi-pass reading is likewise refused in Chat rather than escalated. Chat mode does not initialize the action or reading infrastructure on send, on refresh, or when deleting a chat, so an ordinary chat stays an ordinary chat. Both modes still share one conversation and one document context, and the mode is frozen per request as before.
- Both modes **share one conversation, one document context, one presenter and one history**, so the same chat continues across the switch with the current PDF and prior turns intact; the mode is only routing and grants no permission (writes still require explicit approval). The unpersisted tab is **New chat** and no longer carries the article title; paper identity comes from the attachment/context system.
