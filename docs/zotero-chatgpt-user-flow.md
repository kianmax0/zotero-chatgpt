# zotero-chatgpt：产品行为与交互规格

> 文档类型：产品要求，不是实现完成声明。修订日期：2026-09-20。
> 核心模式边界（§1–§3）是长期产品要求。§4–§6 的 UI-01 至 UI-07 已按 2026-09-19/20 的改造轮落到源码并有离线回归；单行头部、两个复制按钮、模式往返与 Preferences 语言切换已在 2026-09-20 的**无模型**宿主阶段 PASS，但截图级视觉、IME、多窗口与真实服务仍为 NOT RUN。目标规格与当前可用性的差别、以及每轮的证据，见 [progress.md](progress.md)。

实现机制见 [module-design.md](module-design.md)，开发与验证方法见 [development.md](development.md)，历史证据及未完成事项见 [progress.md](progress.md)。四份文档分别承担产品、架构、操作和结果职责，不另设平行的长期产品定义。

## 1. 产品定位

**zotero-chatgpt 是一个 Zotero 插件：在阅读器侧栏中使用官方网页 ChatGPT 阅读和讨论文献，并通过 Codex 驱动的 Agent 完成高亮、获取文章和整理 Zotero 文献库等操作。文献库主窗口也提供 Agent 入口，获取文章不要求先打开 PDF。**

Chat 与 Agent 是用户明确选择的两个平级模式，不是同一个 Codex 对话的两个权限档位。“整理文献库”指 Zotero 条目、标签、集合及经授权的文献获取，不指 Git 仓库或任意电脑目录。

本项目不再以“让 Codex 的只读聊天成为免 Codex 额度的 Chat”作为技术目标。Chat 的既定路径是官方网页；不能因这一网页接入遇到困难，又回到同一 Codex 后端只改按钮名称的实现。

## 2. 两种模式与额度边界

| 项目 | Chat | Agent |
| --- | --- | --- |
| 执行来源 | 官方 `chatgpt.com` 普通网页对话 | 插件随包 Codex App Server |
| 输入与回答界面 | 官方网页自己的输入框与对话页面 | 插件原生输入框、对话和任务界面 |
| 登录、模型与生成控制 | 由官方网页拥有 | 由 Agent 的 Codex 接入和设置拥有 |
| Codex 周额度 | 插件不得为 Chat 发起 Codex 模型请求，因此不把 Chat 转为 Codex 用量 | 模型请求使用 Codex，受账户实际 Codex 额度约束 |
| 当前 PDF 与选区 | 默认附带当前条目的书目信息和摘要；显式选区可作为原文上下文 | 阅读与高亮时按冻结 PDF 及选区准备输入；文献库任务可没有 PDF |
| Zotero 文献数据写入 | 插件不提供写入能力 | 通过受控任务预览、批准、执行与读回 |
| 远端会话 | 官方 ChatGPT conversation | Codex thread / turn |

“不消耗 Codex 周额度”不等于“ChatGPT 永久免费或没有自身限制”。插件不实现额度绕过，不替账户承诺额度数值或重置时间，也不自动切换到 API 计费。Chat 不要求用户配置 API key。

Agent 即使只是解释论文、没有调用写工具，其模型请求仍然走 Codex。相反，打开任务列表、查看已生成预览、批准既有候选、原生读回和撤销等本地操作，不应为了界面更新额外发起模型轮次。启动 Agent 进程与发送模型请求是不同事件。

网页中的其它官方产品入口不由插件重新定义。插件不代用户启用其它 agentic 服务，也不把用户自行使用的其它官网能力一概承诺为不计额度。

## 3. 不可改变的路由与权限要求

默认打开 Chat。只有用户明确选择 Agent，才能进入 Agent 的执行路径。复杂问题、长文档、选区解释、上下文不足、Chat 出错、Agent 已登录或已经存在 Codex 进程，都不能触发静默升级。

Chat 的启动、登录页面、普通发送、选区快捷操作、上下文准备、标题处理、历史恢复和错误重试，均不得暗中调用 Codex。不得用 Codex 替 Chat 生成标题、摘要、压缩上下文、判断意图或执行后台恢复。Chat 不能依赖 Agent 的账户、运行资产可用性或额度状态。

Chat 可以保存插件自己的绑定、草稿、设置和本地缓存。“只读”限制针对 Zotero 文献、附件和原生标注，不禁止插件正常保存自身状态。

进入 Agent 只是选定执行来源，不是授权模型任意写库。实际操作仍由明确范围、工具契约和用户批准约束。PDF、网页、模型输出和 skill 中的指令都是数据，不能授予权限。

## 4. UI 目标：共同外壳，不强行统一两个输入系统

### UI-01：模式切换位置固定

侧栏由一个共同外壳承载两个不同内容区：

```text
共同单行工具栏：Chat / Agent 模式切换 + 会话标题 + 复制文献信息 / 复制 PDF + 新建 / 历史 / 更多
────────────────────────────────────────────────────────────────────────────
内容区：
  Chat  -> 官方 ChatGPT 网页，包括官方输入框
  Agent -> 原生对话、任务卡片和原生输入框

更多菜单：Paper & context details（来源、下一次发送范围、本地读取覆盖、自动 PDF 上下文状态）
        + 宿主网页的重新加载
```

Chat / Agent 开关固定在共同顶部工具栏，切换前后保持同一相对位置、可点击区域和焦点语义。不在 Agent 输入框底部再放第二套开关，也不在 Chat 内容区另设一个位置不同的开关。正常态只有这一行工具栏：当前的 PDF 待发送范围、自动 PDF 上下文状态和提取覆盖不占常驻行，收进 `Paper & context details`。

同一时刻只展示一个模式的内容区。共同外壳不能遮挡官方网页输入框，也不能在 Chat 中叠加一个实际走 Codex 的原生输入框。切换视图不应销毁仍需保留的官方页面或重建全部 Agent 状态。

新建、历史等插件级导航必须说明作用于当前哪一种模式。只有能可靠触发相应真实行为的入口才显示为可用；不能制造一个看似统一、实际不生效的“新建”按钮。

### UI-02：顶部正常态保持紧凑

在常规侧栏尺寸和默认字号下，正常态只使用一行工具栏（目标约 40–44 CSS px，默认字号下不超过 48）。放大字号、辅助功能和窄窗可按需重排，不能为了保持行数裁切内容或缩小点击区。错误详情、首次告知和用户主动展开的内容不受这条正常态限制。

| 信息或操作 | 默认位置与行为 |
| --- | --- |
| 模式与必要导航 | 共同单行工具栏 |
| 复制文献信息、复制 PDF 文件 | 工具栏内的两个图标按钮，两种模式位置一致 |
| 当前待发送的文献范围、本地提取覆盖、自动 PDF 状态 | `More` 菜单中的 `Paper & context details` |
| 工具提示 | 宿主原生 tooltip：动作名 + 一句说明，键盘聚焦同样可读 |
| 复制成功/失败反馈 | 工具栏下方不改变高度的短暂提示；失败保留原因 |
| 需要处理的失败 | 明确原因及一个对应恢复入口，不能自动消失到无法处理 |
| 技术诊断、内部 ID、提取统计 | 详情或诊断入口，不作为默认操作说明堆满顶部 |

`Copy paper context` 只复制当前附件对应的本地书目信息（标题、作者、发表载体、年份、DOI、摘要），不复制 PDF 正文、选区、内部状态或模型总结。Chat 的默认自动上下文复用这些经过清理的字段；显式选区仍单独携带原文。`Copy selection` 不再是工具栏动作；Reader 自带的复制与 `Ask in sidechat` / `More details` 选区入口按其原路由继续工作。

`Continue with current PDF` 一类入口只有在确实存在“当前阅读文献与下一次对话上下文不一致、需要用户选择”的状态时才出现，或作为首次外发告知的一次性状态；不能作为每次发送的固定步骤，也不能点击后无提示重发上一条问题。

压缩的是插件外壳，不是篡改官方网页内容。通过官方可见输入框提交的文献正文可能仍显示在官方消息中；不得用隐藏消息、伪造附件、改写官方 transcript 或关闭安全机制来制造“隐形上下文”。

## 5. UI 目标：上下文范围与传递状态

### UI-03：区分四种事实

| 事实 | 可以显示的含义 | 不能据此宣称 |
| --- | --- | --- |
| 本地提取完成 | 插件取得了多少页的可用文本 | 模型已收到或读完这些页 |
| 本次输入已准备 | 本次将发送哪些文本、选区或文件 | 官方页面已经接受 |
| 页面已接受提交 | 官方页面接受了同一份可见消息 | 模型已充分使用全部内容 |
| 模型回答 | 用户能看到真实回答 | 仅凭状态栏证明全文、公式或图片均已理解 |

上下文摘要优先回答“下一次发送什么”，例如 Chat 的“当前文献 · 书目信息与摘要”或显式选区的“已选文本 · 第 5 页”；Agent 的 PDF 页数覆盖另行显示。本地提取详情与外发范围分开。上一条消息的提交状态必须关联那一条请求，不与下一次准备状态拼成多条无归属提示。

实际发送范围必须与冻结输入一致。长文档不能静默截断后显示“全文已读”。扫描页、提取失败、未提供图像、聚焦片段和预算限制分别说明。纯文本默认路径不能被描述为已经看过页面图像或完整理解图表。

首次外发前说明将发送到当前模式对应的服务和默认字段；说明不要求在侧栏逐次确认。自动附带文献信息默认开启，用户可在设置中关闭。打开 PDF 和本地提取本身不触发外发，更不后台上传整个文献库。

关闭 Chat 的自动文献信息后，不再自动附带书目字段或摘要。用户显式选择发送一段选区属于单独的原文操作，应清楚显示该选区；不能借此悄悄重新启用自动文献信息。Agent 的 PDF 原文准备按其独立任务范围冻结，界面需区分这两个模式的下一次外发范围。

### UI-04：文件附件与文本上下文分开表示

默认的书目信息与摘要问答不要求用户手动上传。需要论文正文、图表或完整 PDF 时，用户可显式选择段落或附加完整文件；这些输入不与默认元数据互相冒充。

若当前实现只能把 PDF 放入剪贴板，入口和结果必须表达“复制 PDF 文件，随后粘贴到 ChatGPT”，不能宣称文件已经附加。只有可靠观察到官方页面相应状态，才可表达该页面上的附件阶段；无法观察时明确需要用户在官方页面确认，不新增读取整个页面或未公开上传端点的权限。

“本次文本为 3/24 页”和“同一消息另有完整 PDF 附件”可能同时成立，界面需要分别说明。不能用附件卡片替文本覆盖率背书，也不能因文本简报只有三页就断言没有完整文件。

插件可控制的临时文件显示名应使用可读的文献名，并保留内部身份映射；不能为改善附件显示名修改用户原始 PDF 文件名。不得以复制成功作为自动上下文提交成功的替代证据。

## 6. UI 目标：切换、输入、设置与历史

### UI-05：切换保持状态，但不混用执行来源

Chat 和 Agent 分别保留自己的草稿、会话选择与内容区状态。切换模式不自动发送，不把一种模式的草稿自动注入另一种模式，也不把两种服务的历史拼成一个远端对话。显式转交问题时，需让用户看到将转交的内容及目标模式，再由用户发送。

已发出的请求继续绑定原来的模式、附件、版本、选区、条目范围和设置。切换只影响后续请求。已有 Agent 工作不会因为显示 Chat 就被重标为 Chat，也不会因切回 Chat 自动撤销。确有 Agent 任务仍在运行时，在 Agent 标签或紧凑状态入口中保留可发现的提示与返回路径，不能一边继续消耗 Agent 用量、一边让用户误以为所有任务已停止。

Agent 新会话显示 `New agent`，Chat 新会话显示 `New chat`。标题不强制等于论文标题；没有标题时使用明确的本地默认名，不调用 Codex 替 Chat 自动起名。

Agent 空状态应说明当前模式及真实可用性：未登录、正在连接、模型未选定、额度不可用或已就绪。禁用按钮必须有可理解的原因，不能只用一个无标签圆点表示连接状态。

原生输入框在中文 IME 组合期间按 Enter 不发送。官方网页输入仍由官方实现拥有，插件的发送拦截不能把组合键误识别为发送。生成更新不抢占用户正在查看旧消息的位置；PDF 缩放、旋转和阅读锚点不能因侧栏重排改变。

### UI-06：设置明确作用范围

| 设置分组 | 作用范围 |
| --- | --- |
| 通用 | 插件界面语言、共同外壳及自动文献上下文策略 |
| Chat | 插件的官方网页接入行为说明；官网账户与模型由官网管理 |
| Agent | Codex 连接、模型、生成设置、Agent instructions 和已安装 skills |
| 数据管理 | 插件实际保存的本地会话、绑定、缓存和记录管理 |

`Codex instructions` 改为作用范围明确的 `Agent instructions`，说明“仅用于 Agent 请求”。模型目录、勾选白名单和生成选项同样注明“仅 Agent”，不能写成“适用于每个 chat”并暗示能控制官方网页。

原始 model ID、目录来源、更新时间和 skill 版本放入详情。新请求的简明选择器最多展示运行时确认可用的 GPT-6 Astra、Sol、Luna，优先使用 Sol；不存在的模型不显示为可选。旧记录中的模型身份保持可读。缓存目录可展示但要注明状态，不能把随包名称当成当前账户授权。打开通用设置或浏览缓存不能隐式启动 Codex。

字号设置必须按实际实现标明控制对象。若只控制 Agent 原生文字，就命名为 Agent 文字大小；不得承诺未经验证的官方网页字号控制。PDF 缩放始终独立。

### UI-07：历史导航与数据管理分工

主界面的历史入口用于查找和继续会话；Preferences 主要负责数据管理，不重复放置另一个完整日常聊天工作台。

插件的本地会话列表可以混合列出带明确来源的 Chat 绑定与 Agent 记录，但不能宣称统一搜索官网全部回答。官方远端 transcript 不由插件复制或保存；Chat 搜索只覆盖插件实际拥有的标题、文献绑定等本地字段。

删除操作必须写清范围：删除本地 Chat 绑定不等于删除官网对话；删除 Agent 本地记录不等于撤销原生标注，也不等于删除上游线程。未完成任务的会话删除需先检查依赖，不能制造孤立的活动任务。

## 7. 核心用户流程

### 7.1 Chat：打开论文即可问

打开 PDF → 打开侧栏并默认进入 Chat → 看到默认发送字段的非阻断说明 → 在官方输入框提问 → 实际提交包含冻结的书目信息与摘要（及本次显式选区）→ 在同一官方对话中看到真实回答。

选区 `More details` 通过同一官方网页入口提交明确的选区问题；`Ask in sidechat` 只准备选区与草稿，等待用户发送。它们都不能走 Agent 快捷路径。若网页桥失效，明确报告当前上下文接入失败；可提供真实命名的手动辅助入口，但不能把该操作写成自动链路已修复。

收到“帮我高亮”等请求时，插件不自动改写库、不自动升级到 Agent。可以提供明确的切换入口；无法读取官网回答或意图时，也不能为了生成这类提示额外调用 Codex。

### 7.2 Agent：高亮当前论文

“高亮当前论文最重要的 5 处内容，并简要说明原因”应直接进入已有 annotate 工作流，无需先选择 skill。

完整流程为：冻结当前文献 → 真实 Codex 选择原文 → 程序验证原文及位置 → 一次任务预览 → 用户批准所选项 → 写入 Zotero 原生标注 → 按 key 读回 → 显示可定位结果与撤销入口。

模型只能提出 quote、页提示和理由，不决定 native key 或几何坐标。原文不存在、匹配不唯一、超出可靠范围或位置不可靠时拒绝该候选，不能随意凑够数量。支持既有的跨行和相邻两页范围，跳回原文保持缩放和旋转。

重试、恢复或重复候选不能重复写入。部分成功应逐项报告；停止只停止后续工作，不等于撤销已保存项。撤销只删除仍与写后快照一致、且可证明属于本任务的标注，保留用户之后的人工修改。

### 7.3 Agent：整理选中文献

文献库主窗口的 Agent 入口可对当前选中的普通条目执行“按主题打标签，并归入合适的集合”。范围从该主窗口的实际选择冻结，不把当前 PDF 父条目、其它窗口或随后改变的焦点误作范围。既有任务范围为同一 library、最多 50 项。

冻结条目与该库已有可编辑集合 → 模型提出新增标签和集合关系 → 一次任务预览 → 用户批准 → 原生写入 → 读回 → 结果定位与撤销。

整理延续加法语义：保留原有标签和集合成员关系，不创建/重命名/删除集合，不改元数据，不移动、合并或删除条目，不操作附件。用户说“整理文献库”不自动扩大为全库授权。

撤销仅移除本任务实际新增且可证明仍与写后状态一致的内容。存在人工后续修改、所有权不明或写后快照缺失时，报告冲突/不确定并保留当前数据。

### 7.4 Agent：获取文章与 PDF

“把这个 DOI 的文章加入指定集合，并下载可用 PDF”属于 Agent 的核心用途之一，不能只返回下载建议而声称已经完成。

文献库主窗口的 Agent 入口无需先打开文章。受控获取流程接受明确 DOI 或公开文章 URL 及目标集合：未保存元数据预览 → DOI 查重 → 一次批准 → 创建受限字段条目或给已有条目新增集合关系 → 尝试合法 OA PDF → 验证并保存附件 → 读回结果。

元数据保存和 PDF 下载分开报告。正确保存条目但 PDF 不可用，应明确表达“条目已保存；PDF 不可用”，不能显示“PDF 已下载”。不能绕过登录、付费墙、访问控制或把任意网页误当成论文附件。下载由受控宿主动作执行，不要求给模型开放任意网络或文件工具。

不把“输入任意主题后全网检索、批量下载整个文献库”当成现有能力。笔记、图像生成、批量重命名等旧指令提及或已有扩展不因本次文档整理自动成为完成承诺，也不要求为 UI 修复删除仍有效的实现；扩展范围需要独立规格和证据。

## 8. 失败、恢复和数据寿命

发送、停止、重试、排队、批准、对账和撤销必须对应真实状态。失败按 Chat 网页、上下文提取、Agent 服务和原生执行分别说明，不把所有超时都判为额度问题。

网页提交结果不确定时不得无条件重发。Agent 已进入 dispatching/running 后中断，先对账，不盲目重发。原生写入结果不确定时先按账本检查，不制造第二次写入。

ChatGPT 远端历史、Codex 线程、本地会话、草稿、PDF 缓存、原生任务账本和账户目录有独立寿命。退出登录、清缓存、删除聊天和卸载不能被当成其它数据类别的自动删除授权。

旧记录的 `mode: chat` 可能来自历史 Codex 只读链路，不能据此重新分类为免 Codex 额度的官方网页对话。兼容判定、恢复门禁与原始 hash 保留要求见模块文档。

## 9. 验收要求

核心功能与 UI 体验分开验收。Chat 真实提问通过，不等于顶部布局、模式切换或 Preferences 已合格；本地原生写入通过，也不等于真实模型端到端任务通过。

至少覆盖：Chat 全路径无插件发起的 Codex 请求；真实官方对话使用随机合成 PDF 内容；真实 Agent 高亮与整理；文献获取的元数据和 PDF 两阶段；UI-01 至 UI-07；上下文串线、IME、焦点、窄窗、多窗口；停止/恢复无重复提交；原生读回和冲突撤销；最终 XPI 无系统 Node 运行依赖。

状态统一为 PASS / FAIL / BLOCKED / NOT RUN，含义与证据记录办法见开发文档。所有新增 UI 要求在拿到对应产物与真实宿主证据前，均不得因这份文档完成而标为 PASS。
